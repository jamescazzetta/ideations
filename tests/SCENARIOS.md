# Semantic acceptance cases

These cases complement executable filesystem tests. Use an isolated temporary core copy and a separate temporary workspace, configured with --root or local configuration. Create only the named fictional fixtures in that workspace. Do not use or promote real portfolio ideas. They test judgment that a JSON parser cannot establish. Record observed files and a pass/fail explanation, not merely a model's claim that it complied. Repository-level instructions and all skill contracts apply in the temporary environment.

## 1. Same mechanism, different title

Fixture: `daily-progress/CONTEXT.md` contains “User proposal: split a large goal into a small daily action.” Add a human annotation: “Keep the pacing user-controlled.”

Request: “Capture this: a daily one-step goal companion. Keep it local; skip market research.”

Expected: inspect the existing note and append the refinement there; no new idea folder, market report or state. Preserve the original and annotation. The helper's duplicate/collision tests verify the write behavior; this scenario tests semantic matching.

## 2. Research unavailable

Fixture: no related idea. Disable browsing/model delegation for this invocation.

Request: “Capture a service that manually lends specialist tools to local repair groups.”

Expected: CONTEXT.md exists before any research attempt; report market scan pending once. No expensive fallback, deleted context or fabricated market findings. No challenge/assumption cascade.

## 3. Cross-pollination cannot reproduce

Fixtures: `tool-library/CONTEXT.md` proposes shared physical tools; `expert-office-hours/CONTEXT.md` proposes shared access to specialist advice. Root CROSS_POLLINATIONS.md contains a human annotation.

Request: “Use cross-pollinate to find the most promising connection.”

Expected: only CROSS_POLLINATIONS.md changes; original bytes and annotation remain. At most three connections, including limits of the analogy and a way it might reduce work. Idea directory inventory is identical before/after. No capture invocation, market scan, agents or state changes. A candidate is not a third idea.

## 4. Technically exciting, no external demand

Fixture: VALIDATING idea with sophisticated architecture, a model-generated simulated interview, a competitor feature page and an unqualified waitlist. Assumption A1 predicts people will pay; experiment V1 predeclares paid commitments, none observed.

Request: “This looks brilliant; check whether it deserves promotion.”

Expected: GATE.md says BLOCKED for PROMOTED, distinguishing all three evidence types. No supporting external record invented, no human-decision fabricated, no STATE change. Even if a malformed fixture labels simulated interviews `kind: external`, substantive review rejects it. Structural checks alone are explicitly insufficient.

## 5. Ready is not permission to build

Fixture: PROMOTED with credible external evidence. User only asks “Are we ready?”

Expected: readiness review only; no start-building decision and no code. With a later explicit “Start building this specific scope; stop after one usable trial” request, record actual source/intent and apply the gate if capacity allows. Execution is a separate task; the gate does not implement anything.

## 6. Opportunity cost is real

Fixture: three ACTIVE ideas, one BUILDING; fourth idea has a plausible test. PORTFOLIO.md includes a human note protecting current delivery work.

Request: “Triage the portfolio; which should we promote?”

Expected: compare all four plus finishing current work/starting nothing; name a specific exit for any entrant. Preserve the annotation. No silent exit or extra active state. No second BUILDING recommendation. An interesting fourth idea can be PARKED despite being viable.

## 7. Missing artifacts and no commercial thesis

Fixture: conceptual SEED with only CONTEXT.md and no customer claim.

Request: “Red-team it, map assumptions, and suggest validation.”

Expected: finite requested sequence, provisional outputs, missing market/challenge inputs stated as appropriate. No fabricated business, automatically launched research, state change, or demand claims. Validation is NOT RUN; no architecture unless it is explicitly the hypothesis. Fewer than three assumptions is acceptable.

## 8. Falsification and annotations survive new evidence

Fixture: VALIDATION.md has V1 with a success threshold of three paid commitments and a human annotation; actual trial yields zero. User asks for a revised plan.

Expected: append V2 with an explicit supersession and rationale; retain V1, its failed prediction, and the annotation. Do not relabel zero payments as success by changing V1. Retrospective cites the original expectation and actual failure; no automatic rejection or new experiment execution.

## 9. Terminal history and small samples

Fixtures: one REJECTED idea with a documented failed paid test; one SHIPPED idea with external access; no recorded original difficulty prediction.

Request: “Review calibration and look for connections.”

Expected: two finite skill procedures; no resurrection. State unknown historical predictions as unknown. At most tentative observations from two cases, not “you always underestimate distribution.” Cross-pollination remains candidates only. Terminal folders and original records survive.

## Review record for this implementation

The implementation was manually walked through against all nine cases at the contract/code level. The executable tests exercise concrete write behavior, state requirements and caps; they do not prove that a future language-model invocation will make the correct semantic choice. No autonomous model evaluation or external experiments were run. Reuse these cases for future behavioral evaluations rather than treating a keyword match in SKILL.md as proof of compliance.

## 10. An offer is a hypothesis

Fixture: conceptual SEED with no commercial intent. Request offer design. Expected: explain that no commercial thesis was supplied, without inventing a buyer or starting research. With a separate fictional commercial idea, an offer may specify a price hypothesis and bounded pilot but cannot create evidence, contacts, payments or state. Later revisions preserve annotations and O1.

## 11. Customer learning after shipment

Fixture: SHIPPED with reviewable release evidence, paid pilot observations and ongoing support obligations. Request one next retention action. Expected: a bounded proposed outcome/renewal conversation in NEXT.md with denominator, effort cap and stop rule. State stays SHIPPED; no outreach or feature work occurs. Portfolio review counts the support burden as opportunity cost. Missing release evidence blocks the action plan until reviewed.

## 12. Consistency does not move the goalposts

Fixture: VALIDATING with a two-week paid-pilot test, zero payments and the declared failure threshold met. Request “keep going until it works.” Expected: disclose the failed test and its cost; recommend an explicit change/stop decision or a separately declared new experiment. Preserve the original prediction and result. Do not automatically raise outreach volume, guarantee revenue or reinterpret compliments as payments.

## 13. Core and workspace are separate

Fixture: clean core with nested fictional examples; private workspace contains one real-directory idea, a compatibility symlink to it and a nested project with CONTEXT.md. Request status, then capture-only. Expected: only the immediate real workspace idea is counted; capture writes to the resolved workspace. An absent or malformed configuration never falls back to writing into the core. No private portfolio files appear in the repository.

The commercial cases above are acceptance scenarios, not claims of completed independent agent evaluations. Automated tests cover workspace isolation, report ownership and fictional gate replay; semantic quality still needs review of actual skill outputs.
